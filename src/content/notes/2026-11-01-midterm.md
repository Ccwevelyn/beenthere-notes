###### Evolution of Enterprise System
1. ** Mainframe Era（1960s–1980s）主机时代**

Batch processing, centralized computing, and limited user interaction

集中式计算：所有计算都在大型主机上完成

批处理（Batch Processing）：每天或每周跑批任务

用户交互极少：通常是命令行或卡片输入

2. ** Client–Server Era（1980s–2000s）客户端-服务器时代  **

Distributed computing, GUIs, networking… relational databases.

分布式计算：客户端负责 UI，服务器负责逻辑

图形界面（GUI）：用户体验大幅提升

网络化：企业开始内部联网

3. ** ERP Era（1990s–Present）ERP 时代  **

Integrated business processes… real-time information… enterprise-wide integration

业务流程整合：财务、库存、制造、销售全部统一

实时数据：企业第一次能实时看到业务状态

标准化流程：企业流程被软件固化

4. ** Web-Based Enterprise Systems（2000s–Present）基于 Web 的企业系统  **

Web accessibility… cloud computing… reduced infrastructure costs.

浏览器访问：不再需要安装客户端

SaaS 模式出现，部署成本下降

5. ** Mobile & Cloud-Native Era（2010s–Present）移动与云原生时代 **

Mobile accessibility… cloud-based infrastructure… microservices architecture.** **

移动化：随时随地访问企业系统

云原生：系统为云而生，而不是迁移到云

微服务架构：系统拆成小服务，独立部署

2. <u></u>**<u>Stable & Robustness</u>**** 稳定性与健壮性  **
+ Server running consistently and correctly under any kinds of legal and illegal operations.
+ Constantly amend and improve to prevent loopholes.  持续修补和改进以防止漏洞  
+ System environmental upgrade to fix potential problems.
3.  **<u>Resilience Control</u>** 弹性控制 / 韧性设计

它解决的问题是：数据丢，机房损坏，火灾、洪水、地震，整个区域的服务不可用

7. **<u>High Availability (HA)</u>**** 高可用性 ** HA 的目标是：**系统永不停机**。  
+ Provide almost zero downtime services (24 × 7).
+ Load balancing, failover, virtual servers, etc.  负载均衡、故障切换、虚拟服务器  
8. **<u>Resource Management & Optimization</u>**<u></u>

 Database, application servers, operating system, network optimization.  企业系统规模大，资源消耗高，因此必须进行系统级优化

##### **<font style="color:rgb(50,55,63);">Multi-tiler Architectures 多层部署架构</font>**
**<font style="color:rgb(50,55,63);">核心问题： 一项请求要经过几个独立的客户端或服务器  </font>**

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/42556572/1793362215615-c74b0d95-7ce3-4487-81a3-e7140db05a75.png)

1.  **<u>两层架构</u>**：客户端直接找服务器  |  Client → Server  
2.  **<u>三层架构</u>**：中间增加业务服务器  |  表示层 → 业务逻辑层 → 数据层   
    - **客户端**：显示界面、接收用户操作
    - **应用服务器**：执行订单计算、权限验证等业务逻辑
    - **数据库服务器**：保存和查询数据

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/42556572/1793362227305-be603e01-75d5-42a0-9d60-92b13f812b49.png)

 **N 层＝继续拆分，各司其职**

+ 浏览器：显示页面
+ Web 服务器：接收 HTTP 请求、提供网页
+ 应用服务器：处理 ERP 业务逻辑
+ 数据库服务器：存储数据

**为什么要拆成更多层？**

因为不同部分的压力不同，可以分别扩展。例如：

+ 网页访问量大：增加 Web 服务器
+ 业务计算量大：增加应用服务器
+ 数据查询量大：增强数据库或增加副本

优点：

+ **Distributed workloads**：分散工作负载
+ **Easy to scale**：容易扩展
+ **Flexibility**：灵活，各层可以独立修改

缺点：

+ **Complexity**：系统更加复杂
+ **Hard to troubleshoot**：请求经过的环节多，故障难排查

##### <font style="color:rgb(50,55,63);"></font>**<font style="color:rgb(50,55,63);">Benefits of layering </font>**
<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/42556572/1793362189971-3d9d6e3b-8636-42fe-8f92-688685b2151b.png)

1. 独立理解：不需要理解其他层
2. 方便替换：只要提供相同的基本服务，就能替换某一层
3. 便于标准化：每层都适合指定统一标准
4. 可以复用：建好一层后，可以被多个上层服务使用
5. 减少依赖：尽量减少各层之间的依赖

#### **<font style="color:rgb(50,55,63);">Ch4. Java Servlets </font>****<font style="color:#DF2A3F;">(Important)</font>****<font style="color:rgb(50,55,63);"> </font>**
A Servlet is a **server-side Java component** running in a web container. It receives an HTTP request, executes application logic, and generates an HTTP response. Servlet 是运行在 Web 容器中的 Java 服务器端组件：**接收 HTTP Request**，执行业务逻辑，**生成 HTTP Response ** 

Servlet 不是独立运行的普通 Java 程序，它运行在 **Web Container（Web 容器）** 中，如 Apache Tomcat, GlassFish...

<u>Web 容器负责</u>：

| Create the Servlet object | 创建 Servlet 对象 |
| --- | --- |
| Manage its life cycle | 管理 Servlet 生命周期 |
| Receive HTTP requests | 接收 HTTP 请求 |
| Map URLs to Servlets | 把 URL 映射到 Servlet |
| Create request and response objects | 创建请求与响应对象 |
| Manage threads | 管理处理请求的线程 |
| Handle security and sessions | 处理安全和会话 |


因此， 容器管理 Servlet，Servlet 处理请求

Servlet 的生命周期由容器管理，包括 `init()`、`service()` 和 `destroy()`。实际开发通常继承 `HttpServlet`，并重写 `doGet()`、`doPost()` 等方法。

** Servlet 接口的五个方法  **

+ `**init(ServletConfig config)**`： Initializes the Servlet.   初始化 Servlet，并接收配置对象。  
+ `**service(req, res)**`： Processes a client request and produces a response.  处理客户端请求并产生响应。  
+ `**destroy()**`：Releases resources before the Servlet is destroyed. Servlet 销毁前释放资源
+ `**getServletConfig()**`：Returns the Servlet configuration object. 返回 Servlet 的配置信息
+ `**getServletInfo()**` Returns information about the Servlet, such as its author or version. 返回 Servlet 的作者、版本或描述等信息。



**三个类之间的继承关系**

1. `Servlet`: 最基础的接口，规定五个方法。**Servlet defines the basic life-cycle contract.**

```plain
public class MyServlet implements Servlet {
    // Must implement all five methods
}
```

2. `GenericServlet`

```plain
public abstract class GenericServlet
        implements Servlet
```

它提供了 Servlet 接口的通用实现，因此开发者不必自己实现所有方法。  
GenericServlet 不特定于某种网络协议。

3. `HttpServlet`

```plain
public abstract class HttpServlet
        extends GenericServlet
```

它专门处理 HTTP 请求，并提供：

```plain
doGet()
doPost()
doPut()
doDelete()
```

+ `service()` 负责分发 dispatches the request，`doXxx()` 负责处理。
+ HTTP Servlet 是一个继承 `HttpServlet` 的 Java 类
+ `HttpServlet` 已经定义了处理各种 HTTP 方法的函数。开发者通过 **override（重写）**，加入自己的业务逻辑辑

##### **<font style="color:rgb(50,55,63);">Java Servlet Lifecycle（p56）</font>**
Servlet 生命周期是 Servlet 从创建到销毁的整个过程： 加载 → 创建 → 初始化 → 服务 → 销毁  

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/42556572/1793501180008-3b7516cf-dc0b-4519-b381-d35c6f8d6994.png)

1. **加载 Servlet**： 类加载器（class loader）负责加载 Servlet 类， 当 Web 容器第一次收到该 Servlet 的请求时，Servlet 类会被加载到 Web 容器中（如 Glassfish）
2. **创建 Servlet 实例**： 加载 Servlet 类之后，Web 容器创建 Servlet 实例， 在一次 Servlet 生命周期中，Servlet 实例只创建一次  
3. **调用 **`**init()**`** 初始化**：Servlet 实例创建成功后，Web 容器调用 `init()` 方法对其进行初始化，`init()` 代表 Servlet 从“已经创建”进入“已经初始化”的状态。这一阶段结束后，Servlet 才能开始处理请求。
4. ** 调用 **`**service()**`** 处理请求**：Servlet 通过 `service()` 方法处理客户端请求， 在生命周期的大部分时间里，Servlet 都处于接收和处理请求的阶段。

```plain
initialized
     ↺ service()
```

```plain
第一个请求 → service()
第二个请求 → service()
第三个请求 → service()
```

5. 调用 `destroy()` 销毁：Servlet 通过调用 `destroy()` 方法结束生命周期，调用 `destroy()` 后，Servlet 结束运行，不再处于已初始化状态。

+ 不适合传密码等敏感内容
+ 按语义不应修改服务器数据

**                            POST 的特点**

+ 通常用于提交或创建数据
+ 参数通常放在 HTTP request body 中
+ 不适合收藏为书签
+ 可能改变服务器状态
+ 传密码时仍然必须使用 HTTPS；POST 本身不加密

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/42556572/1793499296016-686cb786-ba8a-4437-85ad-aa1866656eb1.png)

1. **Web session**： 是用户与 Web 应用之间的一段“对话”或连续交互  

例如，login -> buy stuff -> logout，这几个操作不是彼此无关的请求，而是同一个用户从登录到退出的完整使用过程，属于同一个session。

2. **Session data**： 是保存在服务器上、专属于某一次会话的信息  

例如：`user info`：用户信息，`shopping cart`：购物车内容

 **Session 是交互过程，Session Data 是这段过程中需要记住的信息。  **

3. **Session ID**：应用服务器使用 Session ID 来维持和识别 Session， Session ID 通常是一个 UUID，也就是一个具有唯一性的编号，告诉服务器当前请求属于哪一个 Session，服务器通过 Session ID 将请求与正确的 Session 对应起来

多个用户会同时访问服务器。服务器需要判断：

+ 当前请求来自哪个会话
+ 应该使用哪一份用户信息
+ 应该读取哪一个购物车

**<u>服务器如何维持 Session？</u>**

**<u>方法一：Cookies（</u>**`**<u>jsessionid</u>**`**<u>）</u>**

**第一次 HTTP 请求**，用户第一次访问时，服务器：

1. 创建一个 Session
2. 生成 `jsessionid`
3. 将包含 `jsessionid` 的 Cookie 放在 HTTP Response 中
4. 发送给客户端

**后续 HTTP 请求**，客户端在后续请求中带上这个 Cookie， 服务器读取这个 ID，并识别对应的会话  

**<u>方法二：URL Rewriting</u>**

如果使用 URL rewriting，Session ID 会被加入 URL：

```plain
https://localhost:8080/myapp/somerequest.html; //原来的请求地址 
jsessionid=1A530637289A03B07199A44E8D531427 //附加在地址中的 Session ID
```

客户端访问这个 URL 时，服务器可以从 URL 中读取 `jsessionid`，从而识别 Session。

| **方法** | **Session ID 放在哪里** |
| :---: | :---: |
| Cookie | Cookie 中 |
| URL rewriting | URL 中 |
